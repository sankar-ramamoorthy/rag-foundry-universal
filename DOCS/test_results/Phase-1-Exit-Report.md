## Exit criteria vs. measurements

Benchmark repo: 2,000 files → **56,000 artifacts, 104,000 relationships,
54,000 chunks** (synthetic, generated by the harness). Hardware: laptop
(Windows 11, CPU-only Ollama with `mxbai-embed-large`), Postgres 15 +
pgvector in Docker.

### 1. "Benchmark repo (2k files) ingests < 2 min"

| Stage | Time | Phase 1 target |
|---|---|---|
| Graph build (WP-S1) | **42.7 s** | < 60 s ✅ |
| Atomic persist, 56k nodes + 104k edges (WP-S3) | **25.7 s** | < 30 s ✅ |
| canonical_id → document_id map (F-08) | 1.0 s | single query ✅ |
| Chunking all 54k artifacts (F-08) | 1.2 s | — |
| **Pipeline total (excl. embedding)** | **≈ 71 s** | **< 2 min ✅** |
| Embedding (measured rate, projected total) | 2.2 chunks/s → ≈ 7 h | ❌ hardware-bound |

The ingestion *pipeline* meets the target. End-to-end wall time is
dominated by the embedder: CPU-only Ollama sustains ~2.2 chunks/s on
realistic ~800-char code chunks regardless of pipeline shape (F-08
batching removed the per-chunk HTTP overhead; what remains is model
inference). Meeting < 2 min end-to-end at this scale requires a GPU
embedder, a smaller embedding model, or a hosted embedding API — a
deployment choice, not a further pipeline fix. (For calibration: the
21-file `shared/` tree ingests end-to-end, embeddings included, in well
under a minute.)

### 2. "Vector search uses index"

- `EXPLAIN` on the production query shape shows
  `ix_vector_chunks_hnsw` (verified both in the benchmark and by CI

  **p50 58.1 ms, p95 61.7 ms** (WP-S4 target: p95 < 100 ms ✅; the 1M-row
  load test remains future work as scale grows).
