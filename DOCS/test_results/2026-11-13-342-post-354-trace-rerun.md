# #342 graph-trace rerun after the #354 re-ingestion

## Setup

- **Owner actions.** The owner deployed a release containing #354 (`c0feae2`)
  to the Linux development host. They then ran an incremental re-ingestion of
  the self-repository through Gradio, after backing up the database: ingestion
  `8cbedbb9-9ad6-4c63-83f7-2b7d7659f7e5`, completed.
- **Active generation, verified read-only.** `8cbedbb9`, status `ready`,
  `is_incremental: true`, parent `e423d1bb`, **commit `9f039c4`**. The
  ingestion, vector-store and orchestrator services all report `git_sha`
  `9f039c4`. The generation was unchanged before and after the run.
- **Live run.** `scripts/discovery_diagnostic_342.py` was re-run against
  `8cbedbb9` using the new `--expected-generation` option. It used read-only
  HTTP only: graph export, `GET /v1/repos/{id}/trace` and vector
  `search-by-doc`. The raw record is `2026-11-13-342-post-354-discovery.json`.
- **Same-revision control.** The baseline generation was built from `8e06335`.
  Between `8e06335` and `9f039c4`, 212 files changed, 9 of them in the chain,
  so live before/after numbers mix the fix with code growth. To isolate the
  fix, `scripts/validate_354_import_resolution.py` rebuilt a disposable
  `git archive 9f039c4` corpus in memory, once with the fix off and once on.
  The raw record is `2026-11-13-354-validation-at-9f039c4.json`.

There was no re-ingestion by the agent, no retrieval or ranking change, no SQL
and no generation. Arm A (vector) in the live raw record is reused from the
#351 capture of `e423d1bb`; it was not recomputed and is not discussed here.

The trace used the deployed `/trace` endpoint: forward, depth 6, server cap 300
nodes.

**Depth reached by each chain node** after #354 (`HANDLED_BY,CALL`):

- depth 1: `rag_endpoint`;
- depth 2: `run_rag`;
- depth 3: `resolve_repo_id_http`, `get_embedder`, `hybrid_retrieve`;
- depth 4: `OllamaEmbedder`, `_query_generation`.

Following service edges also reaches the `POST /v1/vectors/search` route at
depth 5. `similarity_search` (depth 6) is not reached, because the 300-node cap
truncates the walk first.

This satisfies #354 acceptance criterion 4. The trace reaches `run_rag`,
`hybrid_retrieve`, `resolve_repo_id_http`, `get_embedder` and
`_query_generation`, and the diagnostic reports H2 as `exact`.

## Findings by category

### 1. Confirmed #354 improvements

- H2 `rag_endpoint → run_rag` changed from a placeholder to an exact CALL edge
  in the live graph.
- The route trace (`HANDLED_BY,CALL`) went from reaching 1 to 7 of 13 chain
  nodes: `run_rag`, `resolve_repo_id_http`, `get_embedder`, `hybrid_retrieve`,
  `OllamaEmbedder` and `_query_generation`. This meets #354 acceptance
  criterion 4.
- The existing expansion policy, seeded with the handler, now yields a
  resolvable `run_rag` (0 resolvable before).
- **Same-commit attribution.** At `9f039c4`, turning the fix on resolves 1,335
  CALL edges and cuts `src.` placeholders from 1,368 to 33, with 0
  correctness violations. The live graph equals that fix-on build.

### 2. Remaining call-representation limitations (in-repository)

- **Functions passed as values.** `asyncio.to_thread(embed_query, …)` (H7) and
  `asyncio.to_thread(store.similarity_search, …)` (H15) are not CALL edges, so
  `embed_query` and `PgVectorStore.similarity_search` are unreachable.
- **Abstract dispatch.** `embedder.embed` (H8) stays a placeholder. The graph
  has `OllamaEmbedder.embed OVERRIDES BaseEmbedder.embed`, but `MockEmbedder` is
  also a candidate, so any resolution must keep that ambiguity.
- **External and SQL hops.** Ollama `/api/embed` (H9) and pgvector `<=>` (H16)
  are source-only by nature.

### 3. Service-to-route resolution gaps

- `CALLS_SERVICE` names a service, not a route. `hybrid_retrieve` links to
  `compose:docker-compose.yml#vector_store_service`, and following
  `EXPOSES_ENDPOINT` fans out to all 7 of that service's routes. The graph does
  not say that `POST /v1/vectors/search` is the one called (H13). The stored
  text of `hybrid_retrieve` does.
- The ingestion-service calls (H4, H12) are likewise service-level only.

### 4. The 300-node traversal cap (newly binding)

- Before #354 the trace stopped at hop 2, so the cap never mattered. Now
  `HANDLED_BY,CALL` records 277 hops, 183 of which end at placeholders. Adding
  service edges reaches the 300-node cap (`truncated: true`) before
  `similarity_search` at depth 6.
- The cap is `TRACE_MAX_NODES = 300` in the orchestrator settings. Reaching the
  handler needs either fewer breadth hops (for example, not expanding
  placeholders or other routes) or a different budget. Neither was changed or
  tested.

### 5. Changes attributable to the newer source revision, not the fix

- **Graph growth.** Between the generations, nodes went from 10,973 to 13,458
  and CALL edges from 10,251 to 14,089, because 212 files changed between
  `8e06335` and `9f039c4`. The fix itself changes no CALL count; its
  replacements are one-for-one.
- **The `/api/embed` request moved.** The embedding-input refactor took it out
  of `OllamaEmbedder.embed` and put it into a new helper. Exact source evidence:

  At `8e06335` (`shared/embedders/ollama.py`), inside `embed()`:

  ```text
  L66                      f"{self.base_url}/api/embed", json=payload, timeout=(10, 120)
  ```

  At `9f039c4` (`shared/embedders/ollama.py`):

  ```text
  L47     def _post(self, texts: List[str], truncate: bool) -> requests.Response:
  L48         # Finite connect/read deadlines; provider hangs must surface as
  L49         # ingestion failure. This is per HTTP batch, not a job deadline.
  L50         return requests.post(
  L51             f"{self.base_url}/api/embed",
  L52             json={"model": self.model, "input": texts, "truncate": truncate},
  L53             timeout=(10, 120),
  L54         )
  ```

  The live graph links `OllamaEmbedder.embed → _strict` and
  `→ _truncated_query`, then both `→ _post → EXTERNAL_SYMBOL:requests.post`.
  `_post`'s stored chunk text in generation `8cbedbb9` contains `/api/embed`,
  read with `search-by-doc`. So the evidence is intact, one hop deeper. The
  diagnostic's H9 ground truth still names `embed` as the caller, so it scores
  this witness as absent. Moving the ground truth to `_post` is a deferred
  scoring change.

## Limits

- One question on one repository generation.
- The baseline and post-#354 generations come from different commits. The
  same-revision control isolates the fix's effect on graph counts, but the
  live trace comparison spans both.
- `/trace` used the server's defaults: depth 6, 300 nodes. No other limits were
  tried.
