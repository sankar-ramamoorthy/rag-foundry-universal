# #342 graph-trace rerun after the #354 re-ingestion

## Setup

- **Owner actions.** The owner deployed a release containing #354 (`c0feae2`)
  to the Linux development host. They then ran an incremental re-ingestion of
  the self-repository through Gradio, after backing up the database: ingestion
  `8cbedbb9-9ad6-4c63-83f7-2b7d7659f7e5`, completed.
- **Active generation, verified read-only.** `8cbedbb9`, status `ready`,
  `is_incremental: true`, parent `e423d1bb`, **commit `9f039c4`**. The
  ingestion, vector-store and orchestrator services all report `git_sha`
  `9f039c4`. The generation was unchanged before and after the run.
- **Live run.** `scripts/discovery_diagnostic_342.py` was re-run against
  `8cbedbb9` using the new `--expected-generation` option. It used read-only
  HTTP only: graph export, `GET /v1/repos/{id}/trace` and vector
  `search-by-doc`. The raw record is `2026-11-13-342-post-354-discovery.json`.
- **Same-revision control.** The baseline generation was built from `8e06335`.
  Between `8e06335` and `9f039c4`, 212 files changed, 9 of them in the chain,
  so live before/after numbers mix the fix with code growth. To isolate the
  fix, `scripts/validate_354_import_resolution.py` rebuilt a disposable
  `git archive 9f039c4` corpus in memory, once with the fix off and once on.
  The raw record is `2026-11-13-354-validation-at-9f039c4.json`.

There was no re-ingestion by the agent, no retrieval or ranking change, no SQL
and no generation. Arm A (vector) in the live raw record is reused from the
#351 capture of `e423d1bb`; it was not recomputed and is not discussed here.

## Graph trace from `POST /v1/rag`

The trace used the deployed `/trace` endpoint: forward, depth 6, server cap 300
nodes.

| | Baseline `e423d1bb` | After #354 `8cbedbb9` |
|---|---|---|
| H2 `rag_endpoint → run_rag` | placeholder `EXTERNAL_SYMBOL:src.core.service.run_rag` | **exact CALL edge** |
| `HANDLED_BY,CALL`: hops recorded, truncated | 7, no | 277, no (183 end at placeholders) |
| `HANDLED_BY,CALL`: chain nodes reached | 1 of 13 (`rag_endpoint`) | **7 of 13** |
| adding `CALLS_SERVICE,EXPOSES_ENDPOINT`: hops, truncated | 7, no | 300, **yes (cap)** |
| adding service edges: chain nodes reached | 1 | 8 |
| Existing expansion policy seeded with the handler | 6 candidates, 0 resolvable | 6 candidates, 1 resolvable (`run_rag`, ranked first) |

**Depth reached by each chain node** after #354 (`HANDLED_BY,CALL`):

- depth 1: `rag_endpoint`;
- depth 2: `run_rag`;
- depth 3: `resolve_repo_id_http`, `get_embedder`, `hybrid_retrieve`;
- depth 4: `OllamaEmbedder`, `_query_generation`.

Following service edges also reaches the `POST /v1/vectors/search` route at
depth 5. `similarity_search` (depth 6) is not reached, because the 300-node cap
truncates the walk first.

This satisfies #354 acceptance criterion 4. The trace reaches `run_rag`,
`hybrid_retrieve`, `resolve_repo_id_http`, `get_embedder` and
`_query_generation`, and the diagnostic reports H2 as `exact`.

## The live graph matches the validated build

| Measure | Live `8cbedbb9` | In-memory fix-on at `9f039c4` |
|---|---:|---:|
| CALL edges | 14,089 | 14,089 |
| CALL edges to placeholders | 10,069 | 10,069 |
| `src.`-prefixed CALL placeholders | 33 | 33 |
| IMPORTS / DEFINES / INHERITS / OVERRIDES | 2,203 / 7,072 / 113 / 21 | 2,203 / 7,072 / 113 / 21 |

The re-ingestion applied the fix exactly as validated. The re-ingestion was
incremental, yet it rebuilt every edge, including those of unchanged files.
This confirms the earlier code-reading claim. The live export has 13,458 nodes
against 13,240 in memory; the extra nodes are the route, compose and
service-topology nodes added outside `RepoGraphBuilder`.

**Effect of the fix alone at `9f039c4`** (fix off → fix on):

- `src.` placeholders fell from 1,368 to 33.
- 1,335 CALL edges were resolved, plus 520 IMPORTS, 5 INHERITS and 13 derived
  OVERRIDES.
- Correctness checks: 0 real edges lost or retargeted, 0 cross-project edges,
  0 added edges without a matching placeholder, 0 shadowed imports.

**The 33 remaining `src.` placeholders are correctly unresolved.** 31 are calls
from files under no project root (`DOCS/`, `scripts/`). The other 2 are method
calls on local string variables named `src` (`src.count`, `src.rstrip`) in two
ingestion tests.

The jump in CALL edges between generations (10,251 → 14,089) is mostly code
growth, not the fix.

**H9 is a source change, not lost evidence.** The embedding-input refactor
between the two commits moved the `/api/embed` request from `embed()` into a
new `OllamaEmbedder._post`. The live graph links
`embed → _strict / _truncated_query → _post → EXTERNAL_SYMBOL:requests.post`,
and `_post`'s stored text contains `/api/embed`. The diagnostic's ground truth
still names `embed` as the caller, so it reports this witness as absent.
Updating the ground truth to `_post` is a scoring change, deferred.

## Remaining gaps, all outside #354

1. **Functions passed as values.** `asyncio.to_thread(embed_query, …)` (H7) and
   `asyncio.to_thread(store.similarity_search, …)` (H15) are not CALL edges, so
   `embed_query` and `PgVectorStore.similarity_search` are unreachable.
2. **Abstract dispatch.** `embedder.embed` (H8) stays a placeholder. The graph
   has `OllamaEmbedder.embed OVERRIDES BaseEmbedder.embed`, but `MockEmbedder`
   is also a candidate, so any resolution must keep that ambiguity.
3. **Route-level HTTP.** `CALLS_SERVICE` names the vector-store service, not
   `POST /v1/vectors/search`. Reaching `similarity_search` fans out to all 7
   routes of the service.
4. **The trace node cap.** Once hop 2 resolves, breadth matters: 183 of the 277
   CALL-only hops end at placeholders. With service edges, the 300-node cap is
   hit before the vector-store handler.
5. **External and SQL hops.** Ollama `/api/embed` and pgvector `<=>` remain
   source-only by nature.

## Limits

- One question on one repository generation.
- The baseline and post-#354 generations come from different commits. The
  same-revision control isolates the fix's effect on graph counts, but the
  live trace comparison spans both.
- `/trace` used the server's defaults: depth 6, 300 nodes. No other limits were
  tried.
