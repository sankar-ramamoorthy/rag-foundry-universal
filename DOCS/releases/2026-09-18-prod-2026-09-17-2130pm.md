# Production Release Record — prod-2026-09-17-2130pm

## Outcome summary — read this before the tables below

**`scripts/prod-refresh.sh --deploy` itself did not complete successfully
on either of the two attempts run against this SHA.** Do not read this
record as "the script passed." The accurate sequence, both times:

```text
deployment started (build + OCI provenance checks: pass)
        ↓
docker compose up -d
        ↓
ingestion-service / llm-service marked unhealthy by Docker
(no start_period configured; ~25-40s retry budget was too short
 for uv-resolved container startup -- see #188)
        ↓
Compose aborts dependent container startup (depends_on: service_healthy)
        ↓
script exits nonzero; release record auto-written as status: incomplete,
with Running-container labels / bind-mount / health / corpus / smoke-query
checks all "not run" (the script never reached them)
        ↓
containers that were marked unhealthy converged to healthy on their own,
unattended, within ~3 minutes
        ↓
(2nd attempt only) rag-orchestrator / gradio-ui, never started by Compose
because their dependency was unhealthy, were started manually
(`docker start rag-orchestrator gradio-ui`) and became healthy
~1 minute later
        ↓
independent post-deploy verification (this session + operator,
2026-09-18, over Tailscale HTTP + docker inspect on-host) confirms the
deployed containers are correct, healthy, and serving the approved SHA
```

The fix for the readiness-gate false negative (`start_period: 60s` on
the five app-service healthchecks) is filed as #188 / PR #189 and is
**not yet merged** — it was not part of this release. This record
documents the release as it actually happened: a script failure
followed by unattended (and one manual) recovery to a verified-healthy
state, not a clean automated deploy.

## Startup-readiness incident (both deploy attempts)

```text
T+0        docker compose up -d
T+~8s      ingestion-db (postgres) healthy
T+~14s     vector-store-service healthy
T+34.1s    ingestion-service marked unhealthy -> Compose aborts
           dependent startup
T+39.3s    llm-service marked unhealthy
~T+3m      ingestion-service healthy, llm-service healthy, unattended
           (attempt 2 only, rag-orchestrator/gradio-ui never started by
           Compose since their dependency was unhealthy)
manual     `docker start rag-orchestrator gradio-ui` (attempt 2 only)
~T+1m      rag-orchestrator unhealthy -> healthy, unattended after start
```

Root cause: no `start_period` on any app-service healthcheck (5 retries
x 5s interval + up to 3s timeout ~= 25-40s total budget), combined with
container startup that took 25-90s before the health endpoint answered
at all — even though the endpoint itself is fast and stable (~0.1-0.2s
per probe) once the app is serving. Likely underlying cause: #41 (`uv
run --directory` resolves each service's environment at container
start, not build time) — not investigated further as part of this
release; #41 remains open and separate. Filed as #188, fix as PR #189
(`start_period: 60s` on the five app-service healthchecks), CI-green,
**not merged as of this record**.
