# Production Release Record — prod-2026-09-17-2130pm

## Outcome summary — read this before the tables below

**Neither `scripts/prod-refresh.sh --deploy` nor the deployed application
was fully correct at the moment this release first came up.** Do not
read this record as "the script passed" or "the deployment was clean."
This release surfaced two independent, previously-undiscovered
deployment-process defects — filed separately as #188 and #191 — neither
visible from ordinary RAG smoke tests. Accurate sequence:

```text
1. Images built from approved SHA 372f82a...; OCI provenance checks pass.
2. `docker compose up -d` hits the healthcheck start_period readiness-
   gate defect (#188): ingestion-service/llm-service marked unhealthy at
   34s/39s (no start_period configured, ~25-40s retry budget too short
   for uv-resolved container startup), Compose aborts dependent startup,
   script exits nonzero. Release record auto-written as status:
   incomplete, with Running-container labels / bind-mount / health /
   corpus / smoke-query checks all "not run" (script never reached them).
   Reproduced on both deploy attempts against this SHA.
3. Services subsequently reach healthy state unattended (~3 min); on the
   2nd attempt, rag-orchestrator/gradio-ui (never started by Compose,
   since their dependency was unhealthy) are started manually
   (`docker start rag-orchestrator gradio-ui`) and become healthy ~1 min
   later.
4. Independent post-deploy provenance/health/corpus/RAG validation
   (this session + operator, 2026-09-18, Tailscale HTTP + docker inspect
   on-host) passes: exact SHA on all 5 containers, no source bind mounts,
   all health endpoints, preserved corpus, successful RAG smoke query.
5. Separately, a migration audit (not part of the script's own checks)
   discovers production's applied Alembic head (`20260831_language_col`)
   is one revision behind the deployed code's actual head
   (`20260917_repo_id_on_requests`, WP-R3/#166). The deployed application
   code unconditionally reads/writes `ingestion_requests.repo_id`, a
   column that migration adds — so `DELETE /v1/repos/{repo_id}` and
   `POST /v1/ingest-repo` were both raising `UndefinedColumn` in
   production for the entire window since #166 was first deployed (exact
   duration unknown). Every RAG read-path check that passed above is
   fully consistent with this: none of them touch that column.
6. `alembic upgrade head` applied against production (`20260831_language_col`
   -> `20260917_repo_id_on_requests`), with this session's explicit
   authorization.
7. Verified: Alembic at head; `ingestion_requests.repo_id` column and its
   two indexes present; backfill correct (6/15 rows matched the 6 live
   repos by `document_nodes`, remaining 9 correctly NULL per the
   migration's own documented behavior for non-backfillable rows).
8. Verified (read-only): the exact query shapes that previously raised
   `UndefinedColumn` — `has_active_ingestion_for_repo`'s and
   `list_ingestion_ids_for_repo`'s `WHERE repo_id = ...` filters — now
   execute successfully. The live `DELETE`/`POST /v1/ingest-repo`
   endpoints themselves were deliberately not exercised end-to-end (both
   are mutating calls against production; the schema/query-shape
   evidence above was judged sufficient without adding a ritual mutating
   HTTP call solely for regression evidence).
```

Fixes for both discovered defects are tracked separately and were **not**
part of this release: #188/PR #189 (healthcheck `start_period`, CI-green,
not merged) and #191 (deployment schema-compatibility gate — no fix
implemented yet, issue only). This record documents the release as it
actually happened: a readiness-gate failure, a database one migration
behind the deployed code for an unknown window, and a verified-correct
end state reached only after two rounds of after-the-fact investigation
and repair — not a clean automated deploy.

## Startup-readiness incident (both deploy attempts)

```text
T+0        docker compose up -d
T+~8s      ingestion-db (postgres) healthy
T+~14s     vector-store-service healthy
T+34.1s    ingestion-service marked unhealthy -> Compose aborts
           dependent startup
T+39.3s    llm-service marked unhealthy
~T+3m      ingestion-service healthy, llm-service healthy, unattended
           (attempt 2 only, rag-orchestrator/gradio-ui never started by
           Compose since their dependency was unhealthy)
manual     `docker start rag-orchestrator gradio-ui` (attempt 2 only)
~T+1m      rag-orchestrator unhealthy -> healthy, unattended after start
```

Root cause: no `start_period` on any app-service healthcheck (5 retries
x 5s interval + up to 3s timeout ~= 25-40s total budget), combined with
container startup that took 25-90s before the health endpoint answered
at all — even though the endpoint itself is fast and stable (~0.1-0.2s
per probe) once the app is serving. Likely underlying cause: #41 (`uv
run --directory` resolves each service's environment at container
start, not build time) — not investigated further as part of this
release; #41 remains open and separate. Filed as #188, fix as PR #189
(`start_period: 60s` on the five app-service healthchecks), CI-green,
**not merged as of this record**.

## DB migration incident — discovered and repaired 2026-09-18

- Before repair: production applied head `20260831_language_col`; repo
  head `20260917_repo_id_on_requests` (WP-R3/#166) — **one migration
  behind the deployed application code**, for an unknown duration since
  #166 merged (2026-09-17).
- Affected, unconditionally: `db_utils.has_active_ingestion_for_repo()`
  and `list_ingestion_ids_for_repo()` (both filter on
  `IngestionRequest.repo_id`, called first inside `delete_repo`) and
  `StatusManager.create_request(..., repo_id=repo_id)` (writes
  `repo_id` on every new repo-ingestion row at accept time). Both
  `DELETE /v1/repos/{repo_id}` and `POST /v1/ingest-repo` were raising
  `UndefinedColumn` in production during this window.
- Not affected: every read path this release's own verification
  exercised (RAG queries, `/v1/repos`, the generation endpoint) — all go
  through `document_nodes`, not `ingestion_requests.repo_id`. This is
  why all of those checks passed cleanly despite the underlying defect.
- Repair: `alembic upgrade head` run against production
  (`postgresql://...@100.105.24.12:5434/ingestion_db`, over Tailscale,
  this session, with explicit operator authorization for both the DDL
  and the specific classifier-blocked action). Applied cleanly.
- Post-repair verification:
  - `alembic current` -> `20260917_repo_id_on_requests (head)`
  - `information_schema.columns` on `ingestion_service.ingestion_requests`
    now includes `repo_id`
  - Indexes present: `ix_ingestion_requests_repo_id`,
    `ix_ingestion_requests_repo_status`
  - Backfill: 6 of 15 `ingestion_requests` rows got a non-NULL
    `repo_id`, matching exactly the 6 completed repos in `/v1/repos`;
    the other 9 (document/PDF ingestions and pre-migration rows with no
    `document_nodes` match) correctly remain NULL, per the migration's
    own documented backfill behavior
  - The exact previously-failing query shapes
    (`WHERE ingestion_requests.repo_id = ...`) now execute successfully
    (checked read-only, both against a nonexistent repo_id and the
    self-repo's real ID)
  - The live `DELETE`/`POST /v1/ingest-repo` endpoints were not
    exercised end-to-end as part of this verification — judged
    unnecessary given the schema/query-shape evidence above, and both
    are mutating calls against production
- Process gap this incident exposed: nothing in `prod-refresh.sh` (or
  any other release step) compares the repo's Alembic head against the
  target database's applied head, before or after deploying code that
  may depend on schema the DB doesn't have. Filed as
  [#191](https://github.com/sankar-ramamoorthy/rag-foundry-universal/issues/191)
  — a preflight schema-compatibility gate (fail fast on mismatch,
  require an explicit migrate step), not silent auto-migration on every
  deploy.

## Release outcome

**CORRECT END STATE, REACHED THROUGH TWO DISCLOSED DEPLOYMENT-PROCESS DEFECTS — NOT A CLEAN DEPLOY**

`prod-2026-09-17-2130pm` (SHA `372f82a`, includes #170/WP-R7) is now
correctly running in production, with both delete/repo-ingestion
functionality and the deployed application code verified consistent
with the database schema. Final verified state:

- exact approved SHA on all five running containers (image ID + OCI
  revision label)
- no application source bind mounts
- all health endpoints passing
- preserved existing corpus, no unintended re-ingestion
- successful end-to-end RAG smoke query exercising the deployed change
- database at the correct Alembic head, with the previously-missing
  `ingestion_requests.repo_id` column, indexes, and backfill verified

Unlike `prod-2026-09-12`, this was **not** a clean automated `--deploy`
run, and it did not become fully correct until after-the-fact
investigation, not through the release process itself:

1. Both deploy attempts hit the healthcheck `start_period` readiness-gate
   defect (#188), requiring unattended recovery (attempt 1) or manual
   `docker start` (attempt 2) before containers reached a healthy state.
2. Production's database schema was silently one migration behind the
   deployed application code (#191) — for an unknown duration predating
   this deploy, not caused by it — leaving `DELETE /v1/repos/{repo_id}`
   and `POST /v1/ingest-repo` broken until discovered and repaired as
   part of this record's verification.

Both are recorded as deployment-process defects to fix (#188/#189 and
#191 respectively), not as evidence this specific release's application
code is unsafe. Neither defect was visible from ordinary RAG read-path
smoke testing — both required deliberately checking the paths a normal
smoke test doesn't exercise (Compose's own readiness gate; the database
schema head independent of application behavior).
