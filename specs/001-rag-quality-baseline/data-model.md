# Phase 1 Data Model: RAG Quality Baseline (WP-Q0)

**Spec**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

> **Not a database schema.** These are the fields of the markdown evidence
> table(s) written to `DOCS/test_results/` (research.md Decision 2). No
> Postgres table, column, or migration is created by this feature —
> Constitution Principles I and II are N/A/PASS respectively (see plan.md's
> Constitution Check) precisely because nothing here touches persisted state.

## Evaluation Corpus

What the evaluation runs against — from spec.md's Key Entities.

| Field | Description |
|---|---|
| `repo_id` | The `repo_id` produced by ingesting `shared/smoke_repo` through the existing pipeline |
| `document_ids` | The 2-3 document IDs produced by ingesting the chosen documents (research.md Decision 1) |
| `ingested_at` | Timestamp the corpus was ingested, recorded for reproducibility |

## Known-Answer Question

A ground-truth (question, expected source) pair — 8-12 of these per spec.md FR-002.

| Field | Description |
|---|---|
| `question_id` | Sequential identifier (Q1..Q12) |
| `question_text` | The natural-language question |
| `query_type` | `code` or `document` |
| `repo_id` | Which ingested repo/document set this question targets |
| `expected_canonical_id` | Expected `canonical_id`, for code questions |
| `expected_passage` | Expected passage/excerpt, for document questions |

## Diagnostic Record

One row per question — the six-field surface from spec.md FR-003.

| Field | Description |
|---|---|
| `question_id` | Links to Known-Answer Question |
| `source_present_in_index` | Boolean — did ingestion actually succeed for this artifact |
| `seed_rank` | Rank in top-k vector search, or "absent" |
| `expanded_rank` | Rank after graph expansion, or "absent" / "n/a" |
| `duplicate_count` | Count of near-identical chunks in the top-20 candidate set |
| `repo_leakage` | Boolean — did another repo's content appear in results |
| `end_to_end_answer_quality` | Pass/fail against the expected passage, via the actual production path |

## Failure Classification

Assigned only to questions whose `end_to_end_answer_quality` is "fail" — from spec.md's Key Entities.

| Field | Description |
|---|---|
| `question_id` | Links to Diagnostic Record |
| `category` | One of: `ingestion-defect`, `absent-from-top-20`, `rank-8-to-20`, `top-3-but-poor-answer`, `cross-repo-leakage`, `duplicate-crowding` |

State transition: a question only reaches `Failure Classification` after
`Diagnostic Record.end_to_end_answer_quality = fail`. `ingestion-defect`
short-circuits classification (spec.md Edge Cases) — no further ranking-based
category applies once that's recorded.

## Clean-Context Score

Recorded only for failed questions (spec.md FR-004) — the Scenario 3 output.
Generated by calling the existing `llm_service` `POST /generate` endpoint
with the hand-picked chunks substituted as `context` (research.md
Decision 4) — the same generation path production uses, so its response
already carries the provenance fields below.

| Field | Description |
|---|---|
| `question_id` | Links to Diagnostic Record |
| `grounding` | Pass/fail — does the answer only assert what's in the supplied context |
| `citation` | Pass/fail — does it point back to the right file/symbol/passage |
| `omission` | Pass/fail — did it miss something present in the context |
| `latency_cold` | Generation latency, cold |
| `latency_warm` | Generation latency, warm |
| `model` / `model_alias` / `provider` | From `/generate`'s response — the actual model that served this request (Constitution Principle IV provenance), recorded so it can be compared against the model that served the original end-to-end failure |

## Evidence Artifact

The file produced — from spec.md's Key Entities and research.md Decision 2.

| Field | Description |
|---|---|
| `file_path` | `DOCS/test_results/<date>-wp-q0-rag-quality-baseline.md` |
| `sections` | Evaluation Corpus summary, Known-Answer Question set, Diagnostic Record table, Failure Classification table, Clean-Context Score table, Final Verdict |
| `final_verdict` | The go/no-go decision on reranking plus failure-count breakdown (spec.md FR-006), or the identified next lever if reranking isn't justified |
